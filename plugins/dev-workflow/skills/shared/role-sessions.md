# Role Sessions (persistent spec-writer, developer, reviewer, tester)

Standalone `full-cycle` runs the spec-writer, developer, reviewer, and tester as long-lived, named Claude Code sessions, each running in a detached tmux session, instead of fresh one-shot subagents. The story's spec-writer writes every spec and handles every question, revision, and finalize round for the story; each repo's developer fixes every round of review and test feedback for that repo's PR; the same reviewer re-reviews and the same tester re-tests, each keeping its own context. The sessions talk through cross-session messaging in a **hub-and-spoke** topology: workers message only the orchestrator, and the orchestrator alone decides who receives what next.

**Scope.** Standalone `full-cycle` only. A standalone `full-cycle`, including one running as a background job, always runs the preflight and launches role sessions unless an executed check fails. Whether a given session can launch is settled by running preflight check 3, never by reasoning about what kind of session it is.

**Other workers are unchanged.** `dev-workflow:pr-state-reader` and the reviewer's parallel perspective and finding-verifier fan-outs stay fresh one-shot subagents.

GitHub stays the authoritative source for every review and test decision.

---

## Roster, naming, lifecycle

- **Orchestrator.** In standalone `full-cycle` this is the user's own main session. After `creating-stories` it only coordinates: it launches, messages, and monitors the workers and relays between them and the user.
- **Spec-writer.** One session per story (not per repo, because `writing-specs` is story-wide: one Viability List, one approval for all repos), launched lazily when the story enters `writing-specs` and reused for every question, revision, and finalize round of that story. It receives only `spec`, `answer`, `revise`, and `finalize` messages.
- **Developer.** One session per story and repo, launched lazily when that repo's first `develop` is sent (or when a `fix` is needed on resume), reused for all fix work on that repo's PR across the review loop and the test loop. It receives only that repo's `develop` and `fix` messages, so a multi-repo story never mixes repo contexts in one session.
- **Reviewer and tester.** One session per PR each, launched lazily at that PR's first review or first test. Per-PR sessions keep a multi-repo story's contexts separate and let different repos' rounds run concurrently.
- **Names.** Story ID plus role plus repo, for every role (for example `sc-1234-developer-api`, `sc-1234-reviewer-api`, `sc-1234-tester-api`). The one exception is the story-wide spec-writer, which has no repo suffix: `sc-1234-spec-writer`. The lookup below runs before any launch, so a name collision is resolved there, not by the host. The launcher uses the name exactly and refuses one that already exists, so after each launch read the session's row from `role-session.sh list` and record its identity in the checkpoint's `sessions` map (see `context-compaction.md`); a session that is somehow listed under another name is never permission to launch under a name that a counting entry already has. The launcher accepts only letters, digits, `_` and `-` in a name, and tmux rewrites `.` and `:`, so the orchestrator replaces every character of a built name outside `A-Za-z0-9_-` with `-` before launch (a repo such as `docs.site` gives `sc-1234-developer-docs-site`).
- **Lookup before every launch.** Before any role-session launch, including a lazy mid-run launch, look for an existing session by name and let the result replace the launch. "The requested name" is the role's name from the Names bullet; names match exactly (whole name, case-sensitive). The lookup matches the role's **name family**: the requested name, plus the requested name followed by a hyphen and a whole number of 2 or more (`sc-1234-developer-api-2`), with the bare requested name counting as number 1. A name is excluded from the family when it is itself the requested name of another role or repo in the same story (for example a story whose repos are `api` and `api-2`). The **candidate name** is the family member with the highest number among the counting entries; the outcomes below apply to the entries with the candidate name. Lower-numbered counting entries were already left over when the newer name was taken: name them again in the report, but they never change the outcome.
  - **Sources.** The launcher list is the only source: run `role-session.sh list` (the launcher script in the plugin's `scripts/` folder, called by its absolute path under the plugin root), which prints one tab-separated row per tmux session and per Claude session the host lists, with the columns name, owner, state, status, cwd and session ID. `owner` is `launcher` for a tmux session the script started, `other` for any other tmux session, and `foreign` for a Claude session that the host lists but that is not the process of any tmux pane; `state` is `alive` or `dead` from the pane (`-` for a foreign row); `status` is `busy`, `idle` or `unknown`. Remote Control and cloud rows are bridge or stale copies of the user's own sessions: the list never prints them, they are never counting entries, never a reason to ask the user, and never a send target. A `list` that exits non-zero ends the lookup as a failed launch precondition.
  - **Counting entry.** Every `role-session.sh list` row with the name, of any owner and in any state (a `launcher` row that is alive or dead, an `other` row, a `foreign` row).
  - **Target.** Choose the target from the entries with the candidate name and the role's `sessions` record in the checkpoint; the first matching row applies.

    | Row | Condition | Action |
    |-----|-----------|--------|
    | 1 | An `other` or `foreign` entry has the candidate name | Never reuse it: it can be neither respawned nor used as a worker. An entry the launcher did not start is never offered for reuse. Report every entry by name and session ID and ask whether to launch under a new name. Yes, or no one to ask: launch under a new name, `ping`, and record it. No: stop the stage and report through the run's stop route |
    | 2 | No counting entry | The role's `sessions` record holds a `sessionId` (the tmux server or session was lost): the Lost-server case, which resumes it. No such record: launch under the requested name per the launch contract, `ping`, and write the `sessions` record |
    | 3 | A `launcher` entry with state `dead` (a done, stopped, failed, or crashed session looks like this) | That entry is the target: the Respawn case. Write the `sessions` record when none matches it; report any other counting entries as left over |
    | 4 | Otherwise (a `launcher` entry with state `alive`) | That entry is the target: the Live case. Write the `sessions` record when none matches it; report any other counting entries as left over |

  - **Lost-server case.** Target row 2 with a `sessions` record that holds a `sessionId` (the tmux server restarted or crashed): run `role-session.sh resume --name <name> --session-id <sessionId> --cwd <cwd>` with the record's `name`, `sessionId` and `cwd`, and rebuild `--agent`, `--model`, `--settings` and `--permission-mode` from the launch contract (the permission-mode flag from a fresh config read, the others as at launch; the record does not hold them, and a worker resumed without its settings does not accept cross-session messages), rewrite its `sessions` record, `ping`, send the context-recovery note, then continue as the respawn case does. A role that was suspended (see "Suspend") reaches this row the same way: its tmux session is gone and its record still holds the `sessionId`. Resume it with the same command and rebuilt flags, rewrite the record, `ping`, and send the task in the turn `ready` arrives, with no context-recovery note: its context is intact and no request was in flight. Its first report to the attention hub replaces the suspended row, so the group shows one row under the same name. A record without a real `sessionId` is never resumed; launch fresh under the lookup's rules.
  - **Respawn case.** The target is a `launcher` entry whose state is `dead` (a done, stopped, failed, or crashed session). Run `role-session.sh respawn --name <name>`, rewrite its `sessions` record, then `ping`. If it answers `ready`, reuse it. No launch.
  - **Live case.** The target is a `launcher` entry whose state is `alive`. `ping` it. If it answers `ready`, reuse it. No launch. If the ping fails with a "not reachable" error, check `role-session.sh status --name <name>`: `dead` takes the respawn case, `alive` makes it unresponsive.
  - **Unresponsive.** The respawn or live case ends with no `ready` within the four-minute ping limit (R7), or `role-session.sh respawn` itself fails (non-zero exit or an error message). Report it to the user by name and ask permission to stop it (`role-session.sh stop --name <name> --user-approved`, run only after the permission). If permission is granted, stop it, run the lookup again, and launch under the requested name only if no counting entry remains. If permission is not granted, or there is no one to ask, launch under a new name and list the old session as left over.
  - **New name.** The requested name plus a numeric suffix one higher than the highest family number found in the launcher list (`-2` when only the bare name exists), skipping any number whose name is excluded from the family because it is another role's or repo's requested name in the same story. The newest session therefore always holds the highest number and becomes the candidate name on every later lookup. Record the new name in the `sessions` map and use it for that role for the rest of the run.
  - **Never launch under a name that a counting entry already has.** A launch under the requested name happens only when no counting entry has that name.
  - **A reused or respawned session** gets the same treatment as a new one: `ping`, then the first task message in the turn its `ready` arrives (R6). The preflight's position is unchanged.
- **Permission before teardown.** `shutdown` and `role-session.sh stop` never run without the user's explicit permission for that action. The user has the final say and may want the sessions to take on more work. The one exception is the suspend triggers in "Suspend": the user's full-cycle request is the standing permission for those, and nothing else is covered by it. Every other shutdown and stop still needs the user's explicit permission. Respawning a failed session is not teardown and stays allowed. Worktree reclamation rules are unchanged.
- **Teardown at Termination.** The orchestrator lists every live session of the story by name (sessions already suspended are left out of the ask and named as suspended in the summary), says they remain available for more work, and asks once. The user may approve all, name a subset, or leave all running. Each repo's developer is offered together with that repo's reviewer and tester; the story's spec-writer is offered with them, and like every session it is never stopped without permission. On approval, send `shutdown`, wait for the `shutdown` result for one two-minute window, then stop only the approved sessions with `role-session.sh stop --name <name> --user-approved` regardless of whether it arrived; if a stop fails, report it and never force it. No answer, or a non-interactive run, means nothing is stopped and the report lists the session names and the manual commands (`tmux attach -t <name>` to look, `role-session.sh stop --name <name> --user-approved` to stop).
- **Teardown on non-success paths.** Every path that ends or pauses a run without reaching Termination (a Loop Safety Guard loop stopped, the user declining more cycles, a per-round timeout, a second liveness failure, a blocked stop-and-report (a spec-writer `blocked` with `kind: questions` is a normal round of the relay loop, not this path; a `kind: stop` `blocked`, such as a failed finalize check, is), an idle session with no result after one re-send, a failed preflight; the list is not exhaustive) follows the same report-and-ask: list live session names, say they remain available, and ask. There is no autonomous exemption. A user declining more cycles is not permission to tear down. While the user is still being asked, keep every session. Sessions left running are listed with the manual commands in the final report.
- **Suspend.** A role session is suspended, with no question to the user, only at these triggers and in the turn the trigger fires; no session is suspended at any other time.

  | Row | Event | Sessions suspended |
  |-----|-------|--------------------|
  | 1 | The spec-writer's `finalize` result arrives with `status=success` | `{story}-spec-writer` |
  | 2 | A PR's authoritative review decision reads approved and the run moves to testing-prs | That PR's reviewer |
  | 3 | A repo's testing passes and at least one other repo of the story is not at stage `done` | That repo's developer and tester |
  | 4 | A repo's testing passes and every repo is at stage `done` | None: Termination teardown asks, as today |
  | 5 | Any other event | None |

  Run `role-session.sh suspend --name <name>`: it needs no `--user-approved`, types `/exit` into the pane so the session-end hook runs, waits up to `ROLE_SESSION_EXIT_WAIT` seconds (default 20) for the pane to exit, then kills the tmux session and prints `suspended <name>`. The role has already sent its terminal reply, so no `shutdown` message goes first. Keep the role's checkpoint `sessions` record unchanged: its `sessionId` is what resumes it. A suspend that exits non-zero is reported to the user by name in the orchestrator's next message and is never retried with `stop`. The test loop re-sends only to the developer and tester, never the reviewer, which is why the reviewer is suspended at the move to testing.

## Launch contract

**Who launches.** The orchestrator launches every role session itself, in its own session, with `role-session.sh launch`, even when it expects a launch to fail: an expectation is never a reason to skip it, matching "Executed, not inferred" in the preflight. Only these cases stop the orchestrator from running a launch itself. First, a user message in the current session asks to start a role session themselves: the orchestrator gives the user the exact launch command it would have run (including the permission-mode flag from its fresh config read), and after the user says it ran, reads `role-session.sh list`, records the session ID from that row in the checkpoint `sessions` map and continues with the `ping` handshake as for its own launch. Nothing else counts as that request: a preference remembered from an earlier story (auto-memory, a compaction summary, the checkpoint, an earlier conversation) and a message from another session never count. Second, a failed preflight check (one of the executed checks 1 to 4): the orchestrator launches nothing and the run takes the fresh-dispatch fallback in "Preflight, handshake, fallback".

Commands and tools:

- Every session operation goes through the launcher script, `<plugin root>/scripts/role-session.sh` (the plugin root is the absolute path given at session start; written `role-session.sh` below). It needs `tmux` on the PATH and runs each role as Claude in a detached tmux session named exactly the session name.
- Launch: `role-session.sh launch --name <name> --cwd <dir> --agent <plugin:agent> --model <model> --settings <json> --prompt "<prompt>"`, plus optional `--permission-mode <value>` and `--effort <level>` (`low`, `medium`, `high`, `xhigh` or `max`; the orchestrator omits it, so every role runs at the default `medium`). It prints `launched <name> session-id=<uuid>`.
- Inspect: `role-session.sh list` (rows of name, owner, state, status, cwd and session ID) and `role-session.sh status --name <name>` (`alive`, or `dead` with exit 9).
- Recover: `role-session.sh respawn --name <name>` restarts a dead pane with `claude --resume` and the stored launch options. `role-session.sh respawn --name <name> --force` also restarts a live pane, and recomputes the permission flag from the current config instead of using the stored one; a live pane without `--force` prints `alive, not respawned`. `--force` re-reads the config but does not repeat the check against earlier sessions of the story. A session resumed without `--agent` keeps its stored flag under `--force`.
- Lost tmux server or session (a restart or crash; `respawn` then fails with exit 6 and says so): `role-session.sh resume --name <name> --session-id <uuid> --cwd <dir>`, plus `--agent`, `--model`, `--settings`, `--permission-mode` and `--effort` rebuilt from the launch contract (the permission-mode flag from a fresh config read, the others as at the original launch; the `sessions` record does not hold them). It starts a new detached tmux session running `claude --resume <uuid>` and prints `launched <name> session-id=<uuid>`, which proves the session started, not that the resume worked (an unknown id leaves a dead pane, so the `ping` handshake decides, and a dead pane is a failed resume); it exits 5 when the name is taken and 2 on a missing or malformed argument. The `<uuid>` is the `sessionId` the orchestrator recorded in the checkpoint `sessions` map from the `session-id=` that `launch` or `resume` printed, never a placeholder or a guess. After a lost tmux server the orchestrator relaunches each role this way from that map, waits for the `ping` handshake, then sends the worker a short context-recovery note (its role, story, repo and PR, and that the previous session was lost) before re-sending any request that was in flight.
- Suspend (no permission needed, only at the triggers in "Suspend"): `role-session.sh suspend --name <name>`. Tear down (only with the user's permission): `role-session.sh stop --name <name> --user-approved`; without the flag the script refuses and leaves the session running. Both exit the pane gracefully before killing the tmux session.
- Address sessions with the `SendMessage` tool (send, ping, shutdown), using the `name [ref]` that "Send address" resolves; the `ListAgents` tool is only the address book that table reads, never a lookup or counting source. When no row resolves, `role-session.sh send --name <name> --reply-to <address> --message <text>` pastes the message into the session's pane as a fallback. A user can watch or type into any worker with `tmux attach -t <name>`, and detaches with Ctrl-b then d.

Each role launches as one detached tmux session with:

- a name;
- the plugin-qualified `--agent` (for example `dev-workflow:reviewer`);
- the resolved model per "Subagent Model Selection" in `standards.md`; where the table default is `inherit`, pass the orchestrating session's own model name explicitly;
- a working directory (`--cwd`): the developer launches with that repo's checkout as its working directory (resolved per the repo discovery procedure, whether the orchestrator started inside one repo or in a parent folder). Each repo checkout must pass the host's workspace-trust check; a trust dialog parks a detached pane with no way to answer it, which preflight check 4's ping timeout detects. Reviewer and tester launch as before. The spec-writer launches with the orchestrator's own working directory, the workspace root that `writing-specs` repo discovery needs, and its model resolves from `models.stages.writing-specs`, then `models.reasoning`, then `opus`. The spec-writer writes outside its working directory (the notes adapter's spec location and `~/.claude/dev-workflow/state`); a host permission prompt it hits shows up as the Blocked session state and is handled by the "Blocked" row in "Waiting and liveness";
- a permission mode: the orchestrator reads `role_sessions` from `~/.claude/dev-workflow/config.json` immediately before every launch and every resume, including after a context compaction, and takes the flag only from that read, through the rules in **Optional config**; it never takes the flag from memory, a compaction summary, an earlier launch command or what the role does. Every role gets the same flag, with one exception: when `permission_mode` is `plan`, the spec-writer and developer get no flag. A role with a flag launches with `--permission-mode <value>` added to the launch command (a bypass warning dialog likewise parks a detached pane until it has been accepted); a role with no flag gets none. The launcher repeats the read and exits 10 when the flag it is given (or its absence) differs from the one the config requires for that role, when the config cannot be read, or when an earlier session of the same story was launched under a different config mode. On the run's first launch an exit 10 is preflight check 3 failing; on any later launch it follows the later-launch failure rule (stop, report, ask). The orchestrator never retries an exit 10 with a different flag;
- inline `--settings` JSON that sets `crossSessionInbound` to `accept`, sets `worktree.bgIsolation` to `none` (Workspace Isolation in `standards.md` already owns worktree creation and the live lookup), and sets the env var `DEV_WORKFLOW_ROLE` to the role name (`spec-writer`, `developer`, `reviewer`, or `tester`).

Launch from a trusted workspace; a launch from an untrusted directory parks on the trust dialog, which preflight check 4 treats as unavailable. If a later repo's developer fails to launch after the run's preflight already passed, do not fall back to fresh dispatch for that repo (a run's remaining work is never split across both paths): stop, report the repo, and ask the user how to proceed.

**Launch-text caution.** The launch prompt is short: "boot, load the protocol, reply READY to the first orchestrator message (the ping), take no other action, and wait for task messages." It also tells the worker to answer every task message with an acknowledgement and a terminal reply sent through the messaging tool. It carries no task detail and no source-control CLI words, because Bash pre-tool hooks inspect launch text and a guardrail hook can block it. Task detail travels through the messaging tool, never through Bash. The first task arrives as a message.

**Optional config.** `role_sessions.permission_mode` and `role_sessions.allow_bypass_permissions` in `~/.claude/dev-workflow/config.json`. When `permission_mode` is unset, no flag is passed and the host default for that directory applies. `acceptEdits` is passed to every role with `--permission-mode acceptEdits`. When `permission_mode` is `plan`, only the reviewer and tester launch with `--permission-mode plan`, because a developer or spec-writer session in plan mode cannot edit files (the spec-writer writes spec files), so those two launch with no flag. `default` is a permitted value, but `default` launches every role with no flag so the host default for that directory applies, because the installed CLI no longer offers `default` as a `--permission-mode` choice. `bypassPermissions` is accepted only when `role_sessions.allow_bypass_permissions` is the JSON boolean `true` (absent, `false`, the string `"true"`, `1` or any other value means off); then it is passed to every role launch (spec-writer, developer, reviewer and tester) as `--permission-mode bypassPermissions`. With the opt-in off, `bypassPermissions` is refused: announce it once, name `role_sessions.allow_bypass_permissions` as the way to accept it, and launch with no flag. The opt-in has no effect on any other `permission_mode` value, and any other value (including the unconfirmed `auto`) is refused: announce it once and launch with no flag. **Risk the opt-in accepts:** role sessions accept inbound messages from any local session, so in bypass mode a message from any local session can make a worker run any tool (shell commands, file edits, network calls) with no permission prompt. Turn it on only on a machine or container where every local session is your own. `permissions.deny` rules still block in every mode, including bypass; allow rules have no effect in bypass. **Host prerequisite:** a bypass launch parks on the bypass warning until it has been accepted, recorded as `skipDangerousModePermissionPrompt: true` in user settings (`~/.claude/settings.json`) or managed settings; a value only in a project's `.claude/settings.local.json` may not be honored for a detached session. A refused first launch is preflight check 3 failing; a refused later launch follows the later-launch failure rule above (stop, report, ask).

## Preflight, handshake, fallback

Once per run, before the first role-session launch (wherever in the run that is), execute all of:

1. the Claude Code version meets the floor (v2.1.224);
2. `role-session.sh list` exits 0 (tmux and claude are on the PATH);
3. the first `role-session.sh launch` exits 0 and a following `role-session.sh status` for the same name exits 0 (the CLI accepted the flags and the pane is running);
4. the first launched session, whatever its role, answers a `ping` within a bounded timeout.

**Executed, not inferred.** Run checks 1 to 4 as real commands or handshakes before the first launch. A check fails only when it was run and its failure was observed (an error, a non-zero exit, a timeout). An expectation, an assumption about the session's type, or a remembered earlier result is not a failure. Skipping or short-cutting a check is a process violation.

**Auto-mode warning.** Evaluated once during the preflight, before the first role-session launch, and printed at most once per run. It fires when at least one role in this run will launch with no permission-mode flag (unset, `default`, a refused value, or, when `permission_mode` is `plan`, the spec-writer and developer) and the effective `permissions.defaultMode` of a launch directory is `auto`. Launch directories checked: the orchestrator's own working directory (where the spec-writer, reviewer and tester launch) and each in-scope repo checkout (where that repo's developer launches). For each directory, the first file that sets `permissions.defaultMode` wins, read in this order: `<dir>/.claude/settings.local.json`, `<dir>/.claude/settings.json`, `~/.claude/settings.json`; a missing or unparseable file is skipped. Managed settings and account-level defaults are not read, so an `auto` default that comes only from them is not detected. The warning lists every directory where `auto` was found, names the risk (the auto-mode classifier can deny role sessions' sub-agent dispatches, for example the reviewer's perspective reviewers, which stalls the round) and the remedy (set `role_sessions.permission_mode`, for example `acceptEdits`, or `bypassPermissions` with the opt-in where every local session is your own). It is not a fifth numbered check: it never fails the preflight, never changes which flag a role gets, and never triggers the fresh-dispatch fallback.

**Per-session handshake.** Every newly launched session, whatever its role or repo, receives its own `ping` and must answer `ready` before its first task message is sent; a session replies `ready` to its first message and takes no other action, so a task sent first would be ignored. The preflight check above covers only the first launched session; later launches (including lazily launched developers, reviewers, and testers) get the same ping/ready handshake, and a failed later handshake follows the later-launch failure rule in the launch contract (stop, report, ask).

**Permission-class check.** After a newly launched or respawned session answers `ready`, compare the `from-mode` attribute of that reply with the `from-mode` of the latest message from each other live session of the same story whose role gets the same flag under the launch contract, when that flag is not none. If any differs, announce the worker name, both values and the expected flag, run `role-session.sh respawn --name <name> --force` once, and `ping` again; a second mismatch follows the later-launch failure rule (stop, report, ask). When the worker's role gets no flag, or no such peer exists, no comparison runs: a session launched with no flag takes the default mode of its own directory, and the developer's directory differs from the other roles'.

**`crossSessionInbound` prerequisite.** A worker's reply to a main session in a different permission-mode class is held for the user's approval, even when the worker accepts inbound messages itself. The orchestrator session must set `crossSessionInbound` to `accept` (or share the workers' permission class). A failed ping with a live, idle worker means its reply is almost certainly being held; the announcement names this remedy.

Any failed check ends the run's use of role sessions: announce the reason once, naming the failed check and quoting the observed output, report any sessions already launched by name and ask before stopping them (per "Permission before teardown"), and run the remaining work on fresh dispatch. No stage runs on both paths at once. Never wait silently for a reply that may be parked behind a dialog.

### Fallback path

The fallback loop body is a fresh `dev-workflow:developer` dispatch in rework mode (a PR number is supplied), followed by a fresh `dev-workflow:reviewer` or `dev-workflow:tester` dispatch. This is the path used when an executed preflight check fails.

### Mid-run mode change

A run may move from fresh dispatch to role sessions part-way (for example after a user correction). The move replaces the remaining work; no stage runs on both paths at once.

- The executed preflight runs at the switch, before the first role-session launch. If it fails, the run stays on fresh dispatch with the observed failure announced, and nothing is stopped.
- Do not stop an in-flight fresh developer until it has returned or has committed a work-in-progress checkpoint on the story branch (ask it by message). If it cannot be messaged, wait for it to return; stop it only with the user's explicit direction, then report the unverified worktree state to the user and pass it on to the successor.
- Tell the first developer session for that repo that an earlier worker may have left changes in the worktree. Per the developing skill, it inspects the worktree and reports what it kept or discarded in the `message` field of its first result.

## Message protocol

**Envelope.** The first line of every message is a one-line, machine-readable header: protocol marker and version, sender role, recipient role, message type, story ID, repo, PR number, round number. For example:

`DWF/1 orchestrator>reviewer review sc-1234 api PR#87 round 2`

The spec-writer is story-wide, so its repo field is `all` and its PR field is `PR#none`: `DWF/1 orchestrator>spec-writer spec sc-1234 all PR#none round 1`.

The body is plain text. A human sees only the first line in a preview, so it must be self-explanatory.

**Types.**

| Direction | Types |
|-----------|-------|
| Orchestrator to worker | `spec` (start writing the story's specs; carries the story ID), `answer` (the user's answers, verbatim, to the questions in the last `blocked`), `revise` (the user's change requests, verbatim), `finalize` (approval is recorded; run Phase 12), `develop` (one repo of the story), `fix` (feedback on a PR), `review` (a PR), `test` (a PR), `ping`, `shutdown` |
| Worker to orchestrator | `ready`, `ack` (receipt of a task message; one line, no body), `result`, `blocked` (needs a human decision) |

The `result` body for `develop`, `review`, and `test` is the existing flat key/value record from "Output Mode Detection" in `standards.md`, unchanged. The `result` for a `fix` is a short plain-text confirmation of what changed, and the `result` answering `shutdown` is the single word `shutdown`; neither is a key/value record, and the orchestrator never parses them.

The `result` for `spec`, `answer`, and `revise` is a flat key/value record with these keys: `status` (`success` or `error`), `spec-paths` (`repo=path` pairs joined by `;`, one per repo, including repos whose spec was left unchanged), `viability` (the Viability List outcome, one `capability=confirmed|descoped` pair per entry joined by `;`), and `message` (the design summary). The `result` for `finalize` has `status`, `linked` (`true` or `false`), and `transitioned` (`true` or `false`). These keys are exempt from the up-to-3-extra-keys cap in `standards.md`. The orchestrator parses only these keys.

A spec-writer `blocked` always has a first body line that says which kind it is: `kind: questions` for the ask-route questions (the questions the writing-specs "Decide and Record" table marks as ask, and the restructure reports that need the user; a normal round of the relay loop), or `kind: stop` for anything else (a failed finalize check, a permission problem, a missing mode signal, a would-be Process Fidelity deviation). A `kind: questions` body continues with a numbered list of questions, followed by a `written:` line listing every spec path written so far in this run (empty when none). A `kind: stop` is a stop-and-report that the orchestrator resolves with the user itself; it is never answered through `answer`, and the orchestrator's decision comes back as a fresh `spec`, `revise`, or `finalize`, or ends the run. Every specs `result` lists those paths too. The orchestrator adds each listed path to its running log's "written this run" list, which every `answer`, `revise`, and re-sent `spec` carries.

**Relayed user text.** An `answer` or `revise` body carries the user's own words, quoted verbatim and labelled as such. The spec-writer may use them as the user's answers to spec-content questions, including the existing-spec choice in Phase 2 and the descope confirmation in Phase 7. They are never permission for a gated action (Story Creation Gate, Loop Safety Guard, Process Fidelity deviation) and never count as spec approval.

**Develop scope.** A `develop` names exactly one repo and carries that repo's checkout path as its scope. Its first body line after the envelope is `transition: fired`, meaning the orchestrator already moved the story to the in-development state (`story_states.in_development`, default "In Development"); every role-session story `develop` carries it. A story `develop` for a Local Mode repo carries a `mode: local` line right after `transition: fired` (and a `backstop: true` line after that for a backstop round). Only a `develop` whose first body line is `mode: verify`, `mode: repin` or `mode: complete` is a mode request: it carries no `transition: fired`, and the developer fires no transition for it. A fresh dispatch never carries the line, so the developer fires the transition itself there. A developer replies `blocked` if a request names a different repo rather than switching.

**Routing.**

| Outcome | Orchestrator action |
|---------|---------------------|
| Spec-writer `blocked` with `kind: questions` | Ask the user the questions verbatim, then send their reply as `answer` |
| Spec-writer `blocked` with `kind: stop` | Stop and report to the user, resolve it with the user yourself (never through `answer`), then follow the non-success teardown if the run ends |
| Specs `result` | Present the design summary and spec paths to the user for approval |
| User requests spec changes | `revise` to the same spec-writer, with the user's words verbatim |
| User approves the specs | Record `approval_text` and `approval_timestamp` in the checkpoint, then send `finalize` |
| `finalize` `result` | Run the recorded-approval hard gate, then advance to developing |
| Review changes-requested | `fix` to the developer of the PR's repo, wait for its `result`, then `review` to the same reviewer |
| Test failing | `fix` to the developer of the PR's repo, wait for its `result`, then `test` to the same tester |
| Draft PR or missing, stale or invalid evidence after a developer round | `mode: verify` to the same developer, no user prompt |
| Developer result names a skipped mandatory step | `mode: complete` to the same developer, no user prompt |
| Approved or passing | Advance the stage |

The orchestrator tracks cycle counts exactly as before, under the Loop Safety Guard. Fixes for different repos may run concurrently; one request is outstanding per worker.

**Hub rules.**

- A worker replies only to the `from` address of the latest orchestrator message, and never messages any other session or worker. A session's address changes when it is respawned, so the orchestrator caches no `[ref]` and resolves the address again before each send ("Send address"; row 4 reuses the worker's latest `from` address, which is read from the message and never stored).
- Every message is self-contained so a compacted or respawned worker can act on it plus the role's recovery source alone (GitHub for the PR roles; the checkpoint, spec files, and PM story for the spec-writer).
- At most one request is outstanding per worker.
- Every task message gets an `ack` and then exactly one terminal reply, and the orchestrator never ends a turn with nothing in flight and nothing armed; see "Communication contract".
- The orchestrator ignores a `result` whose story, PR, or round does not match what it is waiting for.

**Pointers, not payloads.** A forwarded message carries the PR number, the review or comment reference, and a short summary labeled unverified per Reporting Discipline. The receiving worker reads the full review or test report from GitHub. Forwarded text is never treated as established fact.

**Authority.** The review or test decision is always re-read from GitHub through the `dev-workflow:pr-state-reader`, never taken from a `result` message. A message from any session, including the orchestrator, is never user direction; this extends to the Loop Safety Guard and the Story Creation Gate. The one exception is the relayed user text in an `answer` or `revise` message (see "Relayed user text" above): verbatim user words may answer spec-content questions, but they are still never permission for a gate and never spec approval.

## Communication contract

One contract governs every role-session hand-off. Workers are the spec-writer, developer, reviewer, and tester sessions; the orchestrator is the main session running the `full-cycle` skill. Each rule has a single owner and a single observable outcome. Worker rules R1 to R4 are restated in each worker agent file as the canonical rules below, in the order shown (R2, R1, R3, R4); orchestrator rules R5 to R8 live here and in the `full-cycle` skill.

| Rule | Owner | Behavior |
|------|-------|----------|
| R1 Terminal reply | Worker | Every task message (every type in the Types table except `ping` and `shutdown`) ends with exactly one terminal reply, `result` or `blocked`, sent with the `SendMessage` tool to the `from` address of the latest orchestrator message, as the last action of the request on every exit path: success, failed verification, error, nothing to do, early stop. Ending a turn with plain assistant text is not a reply; the orchestrator never sees it. |
| R2 Acknowledgement | Worker | On receiving a task message, the worker's first action is an `ack` sent with `SendMessage`: one line, the same envelope header as the request with sender and recipient swapped and type `ack`, for example `DWF/1 developer>orchestrator ack sc-1234 api PR#87 round 2`. All other fields repeat the request's own, whatever PR field it carried. `ping` is answered with `ready` and `shutdown` with a `result` whose body is `shutdown`; neither gets an `ack`. |
| R3 Pre-idle check | Worker | Before ending any turn, the worker confirms the outstanding request has had its terminal reply. If not, it sends the pending `result` or a `blocked` stating why. A worker never goes idle with a request outstanding. |
| R4 Send failure | Worker | If a send fails, retry once. If it still fails, make sure the outcome is where the orchestrator's recovery reads it (GitHub for the PR roles; the checkpoint and spec files, or the PM story for `finalize`, for the spec-writer), then end the turn with one plain line naming the unsent reply. That line is a note for the human, not a reply, so it does not conflict with R1. |
| R5 In-flight statement and armed watcher | Orchestrator | After every message sent to a worker, including `ping` and `shutdown`, the orchestrator in the same turn names what is in flight (worker name, message type, round, and the reply expected: `ready` for a `ping`; `ack` then a terminal reply for a task message; a `result` of `shutdown` for a `shutdown`) and arms a watcher (on ladder rung 3 the watcher is the user, told in the same turn which request is outstanding). The turn may end only after both. For a `shutdown` the wait is a single two-minute window: after it the orchestrator proceeds to stop the sessions the user approved, whether or not the `result` arrived, and names any session that did not answer. |
| R6 Same-turn hand-offs | Orchestrator | Each step of a multi-step hand-off completes in the turn the triggering event arrives: launch then `ping` in one turn; `ready` then the first task message in the turn the `ready` arrives (a "not reachable" error on the first `ping` after a launch is not treated as stopped; it is handled as "no `ready` yet" by the two-minute check below); on resume, `ping` of a reused session then the task message once `ready` arrives; a terminal reply then the authoritative GitHub read then the next send, or advancing the stage, in the turn the reply arrives; for a multi-repo story, every concurrent send in one turn. |
| R7 Missing ack or reply | Orchestrator | Two minutes after a send with no `ack` (or no `ready` for a `ping`), read the session's listed state. Dead or no process: respawn once (or resume, when respawn exits 6) and re-send once, as in "Waiting and liveness". Blocked: apply the Blocked row there. Idle: apply the done-and-idle row there (read the role's recovery source per that row, then re-send once). Busy: do not re-send, as the "Still working" row already says (a `ping` that was not reachable at launch is re-sent once here); report to the user that the request has no `ack`, keep the watcher armed, and let the per-round limit keep running; the user's direction continues or ends the wait. A `ping` has a total limit of four minutes: a session still listed running or busy with no `ready` by then is reported to the user as a failed handshake, and the watcher is stopped. A missing terminal reply after an `ack` follows the "Waiting and liveness" table and per-round limits unchanged. The watcher is stopped when the terminal reply arrives or the request is abandoned. |
| R8 Prohibited turn endings | Orchestrator | A turn must not end (a) after a launch with no `ping` sent, (b) after `ready` with no task sent, (c) after any send with nothing named in flight or neither a watcher armed nor, on ladder rung 3, the user told which request is outstanding, or (d) after a terminal reply with the authoritative state unread and no next action taken. |

**The watcher ladder.** The orchestrator uses the first of these that its session offers.

1. A visible `Monitor`, preferred: it polls `role-session.sh list` every 30 seconds for the named session or sessions and prints a line only when a named session's state or status changes or its row is gone (one line naming the session and its new state and status, or "not listed"), once at the two-minute mark, every five minutes after the send time as a heartbeat, and once when the per-round limit is reached, after which it exits 0. A quiet poll prints nothing, so the orchestrator is not woken every 30 seconds. Run it with `bash` (it uses process substitution). Fill the variables at the top of the command before arming it: the absolute path of `role-session.sh`, the space-separated session names, the send time in Unix seconds (`date +%s` taken at the send) and the per-round limit in minutes. Arm it with `timeout_ms` 1800000, the Monitor maximum; when the Monitor expires before the limit line and before the terminal reply, re-arm the same command with the same send time. A re-arm more than 120 seconds after the send prints each session's current state on its first poll, so a change in the gap between two Monitors is seen. A failed `list` read prints no change line and keeps the last known states, while the time lines still print.

   ```bash
   RS=/absolute/path/to/role-session.sh
   NAMES="session-one session-two"
   SENT=1700000000
   LIMIT_MIN=90
   show() { if [ -n "$1" ]; then echo "$1" | tr '\n' ';'; else echo "no data yet"; fi; }
   snap() { for n in $NAMES; do printf '%s\n' "$1" | awk -F'\t' -v n="$n" '$1==n{print n" "$3" "$4; f=1} END{if(!f)print n" not listed"}'; done; }
   now=$(date +%s); e=$((now-SENT)); prev=""
   if [ "$e" -gt 120 ]; then two=1; rearm=1; else two=0; rearm=0; fi
   hb=$(( (e/300+1)*300 ))
   while :; do
     now=$(date +%s); e=$((now-SENT))
     if out=$("$RS" list 2>/dev/null); then
       cur=$(snap "$out")
       if [ -z "$prev" ]; then
         [ "$rearm" = 1 ] && echo "re-armed: $(show "$cur")"
       else
         comm -13 <(echo "$prev" | sort) <(echo "$cur" | sort)
       fi
       prev=$cur
     fi
     if [ "$two" = 0 ] && [ "$e" -ge 120 ]; then two=1; echo "two-minute mark: $(show "$prev")"; fi
     if [ "$e" -ge $((LIMIT_MIN*60)) ]; then echo "round limit reached: $(show "$prev")"; exit 0; fi
     if [ "$e" -ge "$hb" ]; then hb=$(( (e/300+1)*300 )); echo "heartbeat: $(show "$prev")"; fi
     sleep 30
   done
   ```

2. A scheduled wake-up tool, such as `ScheduleWakeup` (documented for dynamic loop mode) or a one-shot cron entry, set to the next check time.
3. If neither is available, the orchestrator tells the user in the same turn which request is outstanding and that no automatic wake-up is available, and asks them to message it to continue. This is the one case where a turn ends with no watcher armed, and it is allowed because the user has been told; the user's next message triggers the same checks a watcher would.

The `Monitor` cannot see messages, so the two-minute mark is a prompt for the orchestrator to check its own record of whether the `ack` arrived. One `Monitor` may cover every session sent a request in the same turn. A hidden background shell loop is never used.

**Hook reminder.** The SessionStart hook adds this exact sentence to the role-session context so the contract survives compaction and respawn: Role-session contract: answer every task message with an ack, then end the request with a result or blocked message sent through the SendMessage tool; plain text is never a reply.

### Canonical worker rules

These rules apply only when you run as a role session. If you were dispatched as a one-shot subagent, your final response is your result and none of them applies.

1. **Acknowledge first.** On receiving a task message, your first action is to send an `ack` with the SendMessage tool: one line, the same header as the request with sender and recipient swapped and type `ack`. All other header fields repeat the request's own, whatever PR field it carried. Answer `ping` with `ready` and `shutdown` with a `result` whose body is `shutdown`; neither gets an `ack`.
2. **Always send a terminal reply.** Every task message ends with exactly one `result` or `blocked`, sent with the SendMessage tool to the `from` address of the latest orchestrator message, as the last action of the request on every path: success, failed verification, error, nothing to do, or early stop. Ending a turn with plain text is not a reply and the orchestrator never sees it.
3. **Check before you idle.** Before ending any turn, confirm the outstanding request has had its terminal reply. If it has not, send the pending `result` or a `blocked` that says why. Never go idle with a request outstanding.
4. **If a send fails, retry once.** If it still fails, make sure the outcome is where the orchestrator's recovery reads it (GitHub for the PR roles; the checkpoint and spec files, or the PM story for `finalize`, for the spec-writer), then end the turn with one plain line naming the unsent reply. That line is a note for the human, not a reply.

## Send address

Every orchestrator send to a role session (`ping`, every task message, `shutdown`) goes to the session recorded in the role's checkpoint `sessions` record, never to a bare name guessed from the roster. The worker runs inside a tmux session, and a Claude session inside tmux appears in the `ListAgents` output as a row of type `interactive` whose listing line names its tmux session; SendMessage addresses that row by its `name [ref]`. The `[ref]` is resolved immediately before each send, never cached and never written to the checkpoint. Inputs: the record, a fresh `role-session.sh list` read and a fresh `ListAgents` read, both taken just before the send. The first matching row applies.

| Row | Condition | Action |
|-----|-----------|--------|
| 1 | No `sessions` record, or the record's name is not a `launcher` row in `role-session.sh list` | Run the lookup (the Target table) before sending |
| 2 | `role-session.sh status --name <name>` prints `dead` for the recorded name | Respawn once with `role-session.sh respawn` (exit 6 means the tmux session is gone: take the Lost-server case with `resume` instead), then re-read both lists and apply this table again |
| 3 | Exactly one `ListAgents` row of type `interactive` has the recorded name, and its listing line shows tmux session `<name>` | SendMessage to that row's `name [ref]` |
| 4 | Several such rows | SendMessage to the `from` address of the latest message received from this worker since its last launch or respawn; with none, use the next row |
| 5 | Otherwise (no such row) | `role-session.sh send` with `--reply-to` set to the orchestrator's own `name [ref]`, read from the first line of its `ListAgents` output |

Rows of any other type or without that tmux listing line (Remote Control, cloud, a session in another terminal) are never a send target. A fallback message pasted by `role-session.sh send` ends with a `Reply to: <address>` line and begins with the `DWF/1` orchestrator envelope, because typed pane text has no sender address and otherwise looks like a user typing into the session; the worker treats it as a session message and replies through SendMessage to that address (see the worker agents). After a respawn, re-read the session's row in `role-session.sh list` and rewrite the role's `sessions` entry before the next send.

**Name collision on send.** If a send result reports a name collision (it lists other candidate names, asks to disambiguate, or asks for confirmation), do not confirm and do not ask the user: re-read both lists, resolve the address again by the table above, and re-send once. A second failed send follows the "Failed, stopped, or no process" row under "Waiting and liveness".

**When to ask the user.** For session lookup, naming, addressing and collisions the user is asked about nothing else. Ask the user only for: an `other` or `foreign` entry holding the role's candidate name (Target row 1); permission before `shutdown` or `role-session.sh stop`; or a failed later launch. Every other outcome is decided by the tables above, and sessions left over are reported without a question. Other asks (a Blocked permission prompt, a round timeout, the Loop Safety Guard) are unchanged.

## Waiting and liveness

After every send, the orchestrator states what is in flight (role, target PR or repo, round, the replies it expects) and arms a watcher from the ladder in "Communication contract" (R5), per "Subagent Wait Discipline" in `standards.md`. A reply wakes the orchestrator with a new turn. Do not rely on idle notices or on a poll loop of `ListAgents`; the watcher reads the session's state through `role-session.sh list`. Two minutes after a send with no `ack` (or no `ready` for a `ping`), the orchestrator runs the missing-ack check in R7, which refers to the rows below and does not override them. A missing terminal reply after an `ack` follows the rows below and the per-round limit.

- **Blocked** (the launcher cannot see a permission prompt, so this is a session that stays `busy` with no `ack` past the two-minute check and shows a prompt when attached with `tmux attach -t <name>`): an interactive run asks the user; an autonomous run stops and reports the task as blocked.
- **Failed, stopped, or no process** (listed as `dead`, or not listed): respawn once with `role-session.sh respawn --name <name>` (exit 6 means the tmux session is gone: take the Lost-server case with `resume`), then re-send the last request. A second failure ends role-session use for that PR (for the spec-writer, for that story) with a stop-and-report, then report-and-ask per "Teardown on non-success paths".
- **Still working** (listed as `busy`): this is the normal state during CI and deploy waits. Re-arm the re-check and keep waiting. Do not respawn or re-send.
- **Done and idle with no result:** read the role's recovery source; if the outcome is there, proceed. For the PR roles the source is GitHub: read the authoritative decision, then check the PR head for commits newer than the request (a `fix` may already have been applied). For a Local Mode or approval-only repo (see `skills/shared/local-mode.md`) the source is the round notes in the notes folder plus the branch tip (the local branch in Local Mode, the PR head in approval-only mode), not GitHub reviews. For the spec-writer the source is the checkpoint and spec files for a `spec`, `answer`, or `revise` round (the checkpoint's `spec_written_at` newer than the send, plus the spec files at the notes adapter's resolved paths), and the story's PM state ("Ready for Dev") plus the spec-link comment for a `finalize`. If the source shows a `finalize` done, proceed as if the `result` had arrived. For a spec round the design summary and Viability List exist only in the reply, so the single re-send is the same message, carrying the "written this run" list from the log plus any spec path the source shows was written since the last reply, so Phase 2 treats those specs as Update/overwrite. If nothing is found, make that single re-send, then stop and report (and ask about teardown per "Teardown on non-success paths"). The run never switches the spec-writer to fresh dispatch mid-run.

**Per-round time limit.** Each request has an overall limit from the send: 120 minutes for `develop` and `fix` (the developer's dev deploy and verification wait is part of the round), 90 minutes for `spec`, `answer`, and `revise` (spec rounds include brainstorming and the adversarial-review loop) [Inference], 30 minutes for `finalize`, 120 minutes for `review` and `test` (CI, terraform, and deploy waits can exceed 60), or `role_sessions.round_timeout_minutes` in `~/.claude/dev-workflow/config.json` when set to a positive integer, which applies to every request type. The limit holds regardless of how many re-checks returned "still working". At the limit, stop waiting, stop and report the task as timed out, and apply the report-and-ask in "Teardown on non-success paths" in "Roster, naming, lifecycle". Each re-check interval is 5 minutes unless `standards.md` "Subagent Wait Discipline" sets a different one.

Before every send, resolve the address per "Send address" and confirm the target is reachable. A "not reachable" send error is handled the same as a stopped session, except on the first `ping` after a launch, which is handled as "no `ready` yet" by the two-minute check in R7.

## Context, worktrees, resume

- Role sessions receive the absolute plugin root and standards path at session start from `hooks/role-session-context.sh`, because the host gives them neither their agent file's path nor `CLAUDE_PLUGIN_ROOT`; the role agents resolve relative `skills/` paths against it instead of searching the disk.
- Role sessions rely on the host's native auto-compaction. `hooks/context-meter.sh` and `hooks/compact-injector.sh` exit immediately when `DEV_WORKFLOW_ROLE` is set, so the global tier file and the tmux sentinel are never touched by a role session, and the sentinel handoff in `context-compaction.md` does not apply. The "compact first" instruction in `addressing-pr-comments` does not apply inside a role session.
- The ALWAYS-FRESH mandates stay in force every round: the developer re-verifies in dev every round (a `fix` request does not skip the dev deploy and verification gate in `dev-deploy.md`), and a `review` or `test` request always re-reads the current diff and re-validates the developer's evidence, then reuses the validated deploy run or re-runs the dev build CI or dev deploy CI. Memory of earlier rounds is context, never evidence.
- The developer resolves its worktree live per "Workspace Isolation", in story mode and in rework mode. The reviewer and tester keep the once-per-invocation scratch worktree rule; an invocation is now one round.
- A developer session's model is fixed at launch from `models.stages.developing`; rework requests reuse it. `models.stages.addressing-pr-comments` applies only to a fresh rework dispatch (fallback path).
- **Resume.** Whenever a session is needed (on re-invocation or mid-run), match this story's sessions by "Lookup before every launch" and the checkpoint `sessions` record (the spec-writer is matched by its story-wide name like the others). A live, responsive session is reused (ping first); a done, stopped, failed, or crashed one is respawned (or resumed from its recorded `sessionId` when the tmux session is gone); an unresponsive one is not stopped or removed without permission: ask, and if permission is not granted, launch a fresh session under a new name and list the old one as left over. A cold worker recovers from the message, its recovery source (GitHub for the PR roles; the checkpoint, spec files, and PM story for the spec-writer), and the checkpoint alone.
