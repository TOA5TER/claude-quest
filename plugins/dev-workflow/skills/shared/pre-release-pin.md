# Pre-Release Pin

A dependent repo may pin its reference to an unreleased dependency's pre-release commit instead of blocking on the dependency's merge. This file defines the pin gate used by `full-cycle` and `epic`, the routing for a draft PR whose verification did not finish, and the disclosure the reviewer and tester make on every round. "Per the extension", "git network command", "gh command" and "trusted tag owners" are defined in `local-mode.md` → "Local Mode Extension".

---

## Cross-Repo In-Flight Dependency

Before starting work in a repo that depends on another in-scope repo whose PR has not merged yet (before the orchestrator sends that repo's `develop` message), do not block on that repo's merge without first checking for a published pre-release tag. This is a separate, additional gate on top of the level gate (every PR of the prior level is open), which stays as it is. It applies only to a dependency whose artifact must be merged or published, and it holds only that repo's `develop` message, not other repos'. In fresh dispatch and epic per-task workers there is no per-repo `develop` message, so the insertion point is before the developing stage begins for this repo.

**Local Mode producer.** A producer repo in Local Mode (no pushed PR, no tag) never satisfies a pre-release pin or the level gate. The consumer's `develop` is held until the producer is pushed and merged, which cannot happen within the same run, so the consumer is not developed in this run. This clause takes precedence over the untrusted-owner ask at the end of this section: a Local Mode producer causes a hold, not a mid-run ask. Termination names each held consumer and tells the user to re-run it after the producer is pushed and merged.

**Precondition: no automatic producer.** No skill, agent, or workflow in this plugin cuts a `v{version}-rcN` pre-release tag; publishing one is a human or external precondition to this gate firing at all. Treat step 2 below as a best-effort probe that will usually return nothing until a repo adopts the convention. Its absence is not itself an error.

1. **Determine the target version** by reading the dependency repo's own in-flight PR diff for its version-bump file. What that file is depends on the repo type: `.claude-plugin/plugin.json`'s `version` field for a Claude Code plugin repo; the equivalent manifest field (`package.json`, `go.mod`, `Cargo.toml`, `pyproject.toml`, or similar) for other repo types, meaning whichever file the repo's own release process treats as the version source of truth. If the dependency repo has no discoverable version-bump file, this step cannot resolve automatically. Never guess a version; go to the fallback below.
2. **Resolve a matching pre-release tag by commit, not by name.** This runs from the dependent repo's own checkout, never the dependency repo's, so `origin` names the wrong remote. Address the dependency repo explicitly through the git network command: `<git network command> ls-remote --tags https://github.com/{owner}/{dependency-repo}.git 'refs/tags/v{version}-rc*'`. Never use the repo tags API (unpaginated, with no useful ordering: a repo with many tags can silently miss the match on the first page and produce a false "not found" block). If more than one `-rcN` matches, select the highest N.
3. **Verify before trusting.** `ls-remote` returns SHAs without fetching objects, and the current checkout has neither the tag's nor the dependency PR head's objects locally, so a local `git merge-base --is-ancestor` cannot run. Verify ancestry through the GitHub API, which needs no local objects: `<gh command> api repos/{owner}/{dependency-repo}/compare/{tag-sha}...{dependency-pr-head-sha} --jq .status`. This reports the PR head's status relative to the tag, so the tag is reachable from (an ancestor of) the PR head when `status` is `identical` or `ahead`; reject `behind` or `diverged`. Also confirm the dependency repo's owner is among the extension's trusted tag owners (default: the dependency repo's owner equals the dependent repo's owner). A git tag bypasses branch protection and PR review entirely, so an unverified tag name is not a trust boundary. This path never applies to a dependency repo with an untrusted owner; fall through to blocking on merge in that case, the same as when no tag is found.
4. **If found and verified,** pin the dependent repo's reference to that verified commit SHA, not the tag name, instead of blocking until merge. The pin target travels in that repo's own `develop` message body as the literal line `pin: {dependency-repo} {sha}`, placed after the `transition: fired` line (and after a `mode: local` line, when present), one line per unmerged dependency with a verified pin. The developer's story mode reads it and performs this step after the PR exists: pin the reference as a follow-up commit on the PR's branch, push it, add the warning banner and the `pinned-pre-release: {sha}` line to the PR description, and only then run the dev verification gate once on the pinned HEAD. The pin and banner steps are idempotent, and a failed gate leaves the PR a draft with its banner. A dependency without a verified pin still holds the consumer's `develop` until it merges, so the message is sent only once every dependency has either a pin line or a merge. Fresh dispatch and epic per-task workers carry the same `pin:` lines in the dispatch prompt body. What "pin the reference" means depends on the dependent repo's type: for a Claude Code plugin repo, the dependency constraint exists only as prose in `.claude-plugin/plugin.json`'s `description` field (for example "requires dev-workflow >= 2.23.0"), so pinning means editing that string to name the exact pre-release version and SHA; for a repo with a real dependency manifest (`package.json`, `go.mod`, `Cargo.toml`, `requirements.txt`, or equivalent), pinning means that manifest or lockfile's standard exact-version-or-commit mechanism. Record the pin in the PR description as a literal `pinned-pre-release: {sha}` line: this exact marker is what `reviewing-prs` and `testing-prs` detect and disclose in their reports, not enforce as a gate. Also add a hard warning banner as the very first line of the PR description, before the Summary or any other content, stating that the PR must not be merged until re-pinned to the dependency's final release tag. The Pre-Release Pin Disclosure section below only calls the marker out informationally for `reviewing-prs` and `testing-prs`, so it is the banner, not a review or test gate, that carries the pin's risk forward to the human who approves the merge.
5. **Once the dependency's PR merges** and its final tag is published, the developer re-pins the dependent repo's reference to the final tag's commit. The re-pin is a **re-pin request**: a developer request whose body's first line is `mode: repin`, followed by the PR number and the verified pin target (the dependency repo and the final tag's commit), handled by the developer's re-pin mode. That mode lands a follow-up commit on the dependent PR's existing branch that re-pins the reference, pushes it, runs the dev verification gate on the new HEAD (converting the PR back to draft with its banner and marker if the gate fails), then edits the PR description (REST PATCH form, see "PR Description Updates" in `standards.md`) to remove both the warning banner and the `pinned-pre-release: {sha}` marker line, removes the `tested-in-dev` label, and changes nothing else apart from the evidence comment. The re-pin is never handled as a fix or rework request, because it edits the PR description, which the fixer output-surface rule prohibits for fix requests. **Re-verify rule:** once the re-pin lands, a fresh review and a fresh test run at the new HEAD, bounded by the Loop Safety Guard with a fresh cycle counter. **Fresh-dispatch fallback:** when role sessions are unavailable, the run already fell back, or `full-cycle` is running as an epic per-task worker, send the same request as a fresh one-shot developer dispatch in re-pin mode, with the same first body line. In standalone `full-cycle` there is no tasklist: the re-pin runs only if the orchestrator is invoked again for the story after the dependency's final tag exists, and it runs immediately in that invocation. It sends the re-pin request to the developer session of the dependent PR's repo, resolved by the base resume rule (a live, responsive session is reused; a stopped one is respawned; an unresponsive one is not sent `shutdown`, stopped or removed without the user's permission: ask, and if not granted, launch a fresh session under a new name and list the old one as left over), after repeating the base preflight check first. For a role session the re-pin request is a task message sent under the base Communication contract, so it gets an `ack` and a terminal reply and is followed by the in-flight statement and watcher. A re-pin is sent as a `develop`-type message, but the orchestrator fires no in-development transition for it: the once-per-story transition is tied to the developing stage, never to a re-pin, and a re-pin message carries neither `transition: fired` nor a `pin:` line. With no pin and an unmerged dependency the orchestrator still blocks on merge.

If the target version cannot be resolved, or the dependency repo's owner is not trusted, never guess or silently skip:

- **Interactive mode** (a human can be asked): ask the user directly.
- **Autonomous or dispatched mode** (no way to ask the user, for example `full-cycle` running as an epic per-task worker): do not stop silently or fabricate a version. Return `status: blocked` with a `message` describing the unresolved dependency, so the calling orchestrator can surface it. For an epic-dispatched run, this return value is only a hint: epic's own Resumability reconciliation pass re-confirms authoritative state from GitHub and the PM tool before acting on it, and is what surfaces the block through its blocked-task mechanism.

### Epic Phase 6 readiness override

The epic orchestrator's own context never loads `full-cycle/SKILL.md`, so the readiness computation in epic's Phase 6, which runs in epic's own context, needs the steps restated here. This subsection overrides the Phase 6 scheduler's readiness rule ("a task is ready when every task in its `depends_on` is `done`") for a dependency satisfied by a verified pre-release pin.

**Local Mode producer.** A producer repo in Local Mode (no pushed PR, no tag) never satisfies a pre-release pin or readiness for a dependent task. The consumer's task is held until the producer is pushed and merged, which cannot happen within the same run, so the consumer is not developed in this run. This takes precedence over the untrusted-owner `blocked` handling at the end of this subsection: a Local Mode producer causes a hold, not a `blocked` mark. The end-of-run summary names each held consumer and tells the user to re-run it after the producer is pushed and merged.

A task's `depends_on` entry can be satisfied for scheduling purposes, ahead of the dependency reaching `done`, when all of the following resolve:

1. **Determine the target version.** Dispatch the pr-state-reader against the dependency task's own in-flight PR for its version-bump read (job 5), rather than inspecting the PR diff in the epic orchestrator's own context, per epic's Orchestration-Only Mandate.
2. **Resolve a matching pre-release tag by commit, not by name.** The epic orchestrator's own context is never a checkout of the dependency repo, and `standards.md` forbids `cd` outside the current repository, so a plain `origin` remote has no defined meaning here. Address the dependency repo explicitly: `<git network command> ls-remote --tags https://github.com/{owner}/{dependency-repo}.git 'refs/tags/v{version}-rc*'`; never the repo tags API. If more than one `-rcN` matches, select the highest N that is also reachable from the dependency PR's head commit; reachability is verified in step 3.
3. **Verify before trusting.** Resolve the matched tag to its commit SHA, then verify ancestry through the GitHub API: `<gh command> api repos/{owner}/{dependency-repo}/compare/{tag-sha}...{dependency-pr-head-sha} --jq .status`. The tag is reachable from the PR head when `status` is `identical` or `ahead`; reject `behind` or `diverged`. Also confirm the dependency repo's owner is among the trusted tag owners. Never trust a tag whose commit is not reachable from the dependency PR's reviewed head.
4. **If found and verified,** treat the dependency as satisfying readiness without waiting for `depends_on == done`. Pass the dependency repo, its in-flight PR number, and the resolved commit SHA on the Phase 7 dispatch prompt for the dependent task's orchestrator worker. That worker renders them as literal `pin: {dependency-repo} {sha}` lines (one per dependency) in the body of its fresh developer dispatch, and the developer, not the epic orchestrator, pins the dependent repo's reference to the verified SHA after the PR exists, as a follow-up commit on the PR's branch pushed before any description edit, then writes the banner and marker, and only then runs the dev verification gate once on the pinned HEAD (skipping resolution steps 1 and 2 of the Cross-Repo section above, since the tag and its reachability are already resolved here). Record the pin on the dependent task's tasklist entry as `pinned-pre-release: {sha}`, which is the state step 5 checks for, and also as a literal `pinned-pre-release: {sha}` line plus the warning banner in the dependent PR's description, as in step 4 above.
5. **When the dependency task later reaches `done`** (final tag published and merged), the next resume reconciliation pass (epic's Resumability step 2) checks every task carrying `pinned-pre-release` for a now-completed dependency and, if found, dispatches the dependent task's orchestrator worker to carry out the re-pin. The re-pin is a **re-pin request** with first body line `mode: repin`, handled as in step 5 above, as a fresh one-shot developer dispatch (epic never uses role sessions). **Re-verify rule:** once the re-pin lands, a fresh review and a fresh test run at the new HEAD, bounded by the Loop Safety Guard with a fresh cycle counter. After the re-verify passes, clear the tasklist's `pinned-pre-release` field. **Timing:** the re-pin fires on the reconciliation pass after the dependency reaches `done`, and only for a dependent task parked at `awaiting-merge`; if the dependent is still running its loops at that pass, leave the tasklist field set and let the next reconciliation pass retry. A task carrying `pinned-pre-release` is not eligible for the `awaiting-merge` → `done` transition until the re-pin, the PR-description banner and marker removal, and the tasklist field clear have all landed. This is the explicit hook the base state machine otherwise lacks: without it, a human could merge the dependent while it is still pinned to a tag nobody reviewed.

If the target version cannot be resolved, or the dependency repo's owner is not trusted, do not guess or silently skip the task: mark it `blocked`, record the reason as a comment, and surface it in the end-of-run summary through epic's existing blocked-task mechanism. The `pinned-pre-release` scheduling field in step 4 is the one piece of new state this subsection introduces.

## Draft-PR Resume Routing

When resume detection finds a draft PR (dev verification did not finish), re-run steps 1-3 of the Cross-Repo section above and read the PR description for a `pinned-pre-release` marker, then route:

- Marker present and the dependency's final tag now exists: send a **re-pin** request, not verify. The idempotent re-pin runs the gate, and on success removes the banner, marker, and `tested-in-dev` label and marks the PR ready. This is the recovery path after a failed re-pin gate.
- Marker present and the dependency still unmerged: send a **verify** request (first body line `mode: verify`) with the `pin:` line resolved by this re-run of steps 1-3. The pin steps skip only what already matches that SHA; a marker naming a different SHA is rewritten.
- No marker and a verified pin is needed: send verify with the `pin:` lines; verify performs story mode's pin steps idempotently.
- No marker and no pin needed: send a plain verify.
- Dependency unmerged with no verified pin: send nothing and block on merge, as for `develop`.

An interrupted pinned story is therefore never deployed unpinned or marked ready without its banner. This routing belongs to `full-cycle`; epic never sends developer requests itself.

## Pre-Release Pin Disclosure

This section addresses the reviewer and tester roles. A dependent repo may pin its reference to an unreleased pre-release tag's commit SHA instead of blocking on the dependency's merge, recorded on the PR as a literal `pinned-pre-release: {sha}` line in the PR description. A live pre-release pin is an accepted, intentional state: it is disclosed, not blocked.

Check the PR description for a line-anchored, real-SHA pin marker, not merely a mention of the marker syntax (this section's own prose, or a PR that documents or reviews this feature, must not self-trip the check):

```
<gh command> pr view {PR_NUMBER} --json body --jq .body \
  | grep -E '^pinned-pre-release: [0-9a-f]{7,40}$'
```

If that anchored pattern matches, include a `## Pre-Release Pin Disclosure` section in the review or test report body: quote the matched SHA and note that the PR pins an unreleased dependency commit that must be re-pinned to the dependency's final release tag before merge. Then proceed with the review or test exactly as if no pin were present. This section is informational only: it must never be filed under `## Required Changes`, and neither the pin's presence nor a PR-description warning banner's presence or absence may ever change the APPROVE or REQUEST_CHANGES decision. Re-emit the section on every review and test round for this PR for as long as the anchored marker still matches, including the final approving round, so the human merge-approver who opens that review sees it.

In Local Mode there is no PR description: read the marker from the `pr-draft.md` body instead (same anchored pattern), and when it matches, put the `## Pre-Release Pin Disclosure` section in the review or test note's report body, below the note's first line, exactly as in a GitHub review. In approval-only mode the PR description is read as usual and the section goes in the note's report body (which the plain PR comment repeats). Either way the section is informational only and never changes the `decision=` on the note's first line.

Confirming the pin has been resolved (re-pinned to the dependency's final release tag) before merging is the responsibility of the human who does the final merge approval, not of this gate. The warning banner stamped at the top of the PR description at pin-creation time is what carries that information forward to them. This applies regardless of dispatch path, standalone `full-cycle` or epic-orchestrated.
